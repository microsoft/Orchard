# Known Security Issues

This document tracks known security issues identified by the security team's
threat-model review. None of these are currently remediated in the codebase —
they are documented here so operators are aware of the residual risk before
deploying Orchard to production.

For the full threat model and STRIDE analysis, see
[threat-model.md](threat-model.md). Issue IDs (T-XX) match the threat model.

> **Status:** All issues below are **open / not remediated**. Operators are
> expected to apply compensating controls (network isolation, restricted API
> key distribution, trusted images only) until fixes ship.

---

## P0 — High Risk

### T-17 — Path traversal in file upload / download

- **Where:** [server/api.py](../server/api.py) `upload_file` / `download_file`
  routes and [agent/server.py](../agent/server.py) `/files/upload` /
  `/files/download` handlers.
- **Issue:** The `path` field in file upload/download requests is forwarded to
  the sandbox agent without validation. A caller with a valid API key can
  supply values like `../../etc/passwd` or any absolute path, allowing
  arbitrary read/write anywhere on the container filesystem (including
  service-account tokens at
  `/run/secrets/kubernetes.io/serviceaccount/token` if auto-mounted — see
  T-13).
- **Planned fix:** Two-layer path validation (orchestrator + agent) constraining
  paths to an allow-list of roots (e.g. `/workspace`, `/tmp`, `/home`) and
  rejecting `..` segments.

### T-13 — Service-account token auto-mounted in sandbox pods

- **Where:** [server/k8s_client.py](../server/k8s_client.py) `create_pod()`.
- **Issue:** The pod spec does not set `automountServiceAccountToken: false`,
  so the default service-account token in the `sandbox-pods` namespace is
  mounted into every sandbox at `/run/secrets/kubernetes.io/serviceaccount/`.
  A workload (or anyone exploiting T-17) can read it and use it to query the
  K8s API.
- **Planned fix:** Set `automount_service_account_token=False` on the
  sandbox pod spec.

### T-14 — Redis is unauthenticated and unencrypted

- **Where:** [deploy/k8s/redis.yaml](../deploy/k8s/redis.yaml),
  [server/settings.py](../server/settings.py),
  [server/redis_job_store.py](../server/redis_job_store.py).
- **Issue:** Redis runs without `requirepass`, without TLS, and is exposed via
  a `ClusterIP` service reachable by all pods in the cluster. Any pod that
  achieves code execution can read job stdout/stderr, inject fake job
  results, or delete sandbox records.
- **Planned fix:** Enable Redis AUTH via a Kubernetes Secret, build the
  connection URL from a `REDIS_PASSWORD` env var, and add a NetworkPolicy
  restricting ingress on port 6379 to the orchestrator pods only.

### T-08 / T-09 — Orchestrator → sandbox agent channel is plaintext HTTP

- **Where:** [server/agent_client.py](../server/agent_client.py) `_url()`
  always builds `http://{pod_ip}:8080`; [agent/server.py](../agent/server.py)
  `uvicorn.run()` has no `ssl_keyfile`/`ssl_certfile`.
- **Issue:** All exec stdout/stderr and file contents transit the cluster
  network in plaintext. A compromised node-level component (CNI plugin,
  DaemonSet) or any process that escapes its container namespace on a shared
  AKS node can passively eavesdrop.
- **Planned fix:** Enable mTLS between orchestrator and sandbox agents —
  either self-signed per-pod certificates generated by the agent at startup,
  or a service mesh (Istio / Linkerd) sidecar handling encryption
  transparently.

## Compensating Controls (until fixes ship)

- Treat the `sandbox-pods` namespace as fully untrusted; do not run other
  workloads on the `sbx` node pool.
- Restrict API-key distribution; rotate keys frequently.
- Only run trusted base images that do not contain credentials in standard
  filesystem locations.
- Apply Kubernetes Network Policies at the cluster level to isolate the
  `orchestrator` and `sandbox-pods` namespaces from other namespaces.
- Use only a private Redis instance dedicated to Orchard and isolate it via
  cluster-level NetworkPolicy.
